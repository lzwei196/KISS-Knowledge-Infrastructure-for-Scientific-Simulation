## 1. Approval can record one data source and download another — HIGH

**What happens.** A plan names the data for an input in two places: the data list (which drives the download and the model run) and the "data source" choice shown on the approval card. GeoForge never checks that they match, and the card silently drops any source that is not in the GeoForge Database catalogue (for example the NASA POWER weather provider).

**How a user hits it — with the normal Approve button.** The planner recommends a non-catalogue source (say NASA POWER) while the data list pins a catalogue dataset (say CMFD). The card hides the NASA POWER option, pre-selects nothing, and still says "defaults to NASA POWER unless you pick another". The user clicks **Approve**; no choice is sent; GeoForge signs an approval recording *both* "NASA POWER accepted" and "CMFD", downloads CMFD, and gives the execution agent both as instructions. When every option is non-catalogue the data-choice row disappears from the card entirely, yet the approval still signs the value. The same mismatch happens for catalogue sources whenever an approval arrives without the choice attached (API or other clients); in the browser that case is masked because a pre-checked choice is re-pinned before signing. A real planning session (APEX, Harbin; `docs/issues/APEX-PLAN-AND-ACTIVITY-2026-09-27.md`) produced exactly this plan shape.

**Impact.** The wrong forcing dataset can be used in a scientific run, and the signed approval record cannot be used to audit which data the user accepted. The agent-chosen value is also labelled as a "KI protocol default" in the record.

**Where.** `kiss/kiss_cli/plan_review.py`: `_data_choices` drops non-catalogue ids (~313-316); `picked` is never checked against the options or the item (~337); with no `choices` in the action nothing is re-pinned (~107-126); `decision_records` signs the item (~698-710) and the choice (~738-744) without cross-checking. `ki_tools_common/.../flow/plan.py` only checks that `options` is a list. Existing tests do not cover a choice that disagrees with its item.

**Fix direction.** (1) Before issuing the card, send back any plan whose data-source choice disagrees with the inventory item it governs, or whose pick is not among its options. (2) Show non-catalogue sources as selectable "external" options instead of dropping them. (3) When Approve carries no choice, re-pin to the card's shown recommendation (as the browser path does) or refuse. (4) In `decision_records`, refuse to sign a choice whose value differs from its item.

## 2. Stop / Exit miss agent jobs started through Git Bash wrappers — medium

**What happens.** GeoForge stops work on Windows by following parent/child links between processes. When an agent CLI (Claude Code runs commands through Git Bash) starts a job with `nohup`, and also `timeout`, `env`, `sh -c` or a bash script, Git Bash breaks that link immediately, even while the shell is still running. **Stop** and tray **Exit** then leave that job running until it ends or is killed in Task Manager. The long-job instructions tell agents to use `nohup`, so long ad-hoc runs are the likely case. Receipted model runs (`run-tool`) are stopped normally; files a stray job writes later block **Completed** rather than count.

**Fix direction.** Start each agent CLI and tool in its own Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (no breakaway allowed; assign while suspended), and stop by terminating the job; keep the snapshot walk as a fallback. A prototype stopped every escaped job, including after a Desktop crash.

## 3. Setup turns can run the full scientific model — medium

**What happens.** After approval, software setup is handed to an agent. "Install only; do not run the model" is enforced only for the separate installation-only test, not for in-project setup. In the end-to-end test the setup agent ran the whole FSM2 example and left about 15 MB of results and scripts in the shared software folder. Those results carry no receipt and cannot mark a project complete, but they cost time and tokens and clutter a folder every future project reuses.

**Fix direction.** Treat a setup turn inside a project like installation-only for commands (installation steps and bounded startup probes only); the host already runs the real preflight afterwards.

## 4. Calibration opens a console window per model evaluation — medium

**What happens.** In the packaged app, each calibration evaluation starts the model without hiding its console, so a black window appears for every evaluation (hundreds or thousands per calibration) and stays until that evaluation ends. Closing one makes that evaluation count as a failure. Running from source does not show it.

**Fix direction.** Give the calibration worker one windowless console that model runs inherit (`AllocConsoleWithOptions` with no window where available), without changing the pinned calibration engine.

## 5. Shared Flow fixes not yet on the server; untested areas — medium (process)

- `ki_tools_common/flow/UPSTREAM.json` lists 16 pending edits to the shared Flow package. If the server copy is synced over it ("server = reference") before they are carried upstream, the Windows build breaks: the Flow package would fail to load on Windows (POSIX-only locking), projects could never reach **Completed**, catalogue cards with non-ASCII text would be silently dropped on Chinese Windows, and Claude file permissions would be written in a form Windows does not match. Carry them upstream before the next sync.
- Exercised end to end in the compiled Windows app: FSM2 with the DeepSeek API only. **Not yet exercised:** Codex / Claude / Kimi CLI agents live, GeoForge Database downloads, calibration, and the other KIs. The Windows model-installation snapshot (91 installed / 35 need user action / 1 failed) dates from 2026-09-07.

## 6. Smaller items — low

- **Release tags.** Pushing a `v*` tag (for example `v0.6.55`) from `windows-version` would publish a public multi-platform release whose Windows build is not the tested one. Windows releases use `windows-v*` tags; pushing the branch triggers nothing.
- **No raster reader in the packaged app** (rasterio / pyproj / rioxarray excluded): a delivered GeoTIFF subset covering the wrong area is kept as "pending" rather than rejected.
- **Outdated instructions** inside the bundled GeoForge Database KI docs still name removed tools.
- **Whole-product sizes** from the catalogue (for example CMFD ≈ 649 GB) can be quoted to the planner as if they were the project's download.
- **netCDF4 compression-filter plugins** cannot load in the packaged app (their DLLs ship under different names); compressed netCDF variables using those filters would fail to read.

## 7. Found after release, fixed in source (not yet in a release build)

Found on 2026-10-01 while capturing the 0.6.54 manual. All three are fixed on `windows-version` with regression tests (`kiss/tests/test_chat_turn_delivery.py`); the published `windows-v0.6.54` build still has them.

- **Reloading or closing the browser tab ended the running chat turn — medium.** On Windows a write to a tab that has gone raises `ConnectionAbortedError` (WinError 10053), which the chat stream writer did not catch. The turn then failed with "GeoForge could not finish this turn: ConnectionAbortedError…", and a planning turn reported "The provider failed or was interrupted", while the agent's work was cut off. Pressing F5, closing the tab or a browser restart during planning, setup or a run was enough. Fix: treat any dropped connection as "the browser left" and keep the turn running, collecting its reply for the transcript and the Flow checks; only **Stop** ends a turn. Until the next build: don't reload or close the GeoForge tab while the agent works.
- **The verdict of a run that starts right after setup never reached the chat — medium (all platforms).** When software setup passes after approval, the execution turn starts in the same request. Its Flow verdict ("**Completed.**" or "**GeoForge verification:** not complete yet — … regenerate or remove them: …") was computed and then dropped, so the user saw only the agent's own summary and **Project status** saying "Ready to continue", with no reason. In the manual's FSM2 run the project stopped at "2 steps done, 0 to go, 5 unreceipted files" (files the setup agent wrote into the project, known issue 3) without saying so. Fix: show that verdict like any other turn's. Until the next build: if a run after setup ends without **Completed**, send a message in the chat; the next turn's verdict is shown.
- **Archiving a chat failed silently when a project file was open — low.** Windows will not move a folder while another program (File Explorer, Excel, an editor, a running model) has a file in it open. The archive request then dropped its connection and the sidebar ✕ did nothing. Fix: the server answers with a clear "file … is open in another program" message and the page shows it. Until the next build: close programs using the project folder, then archive.

## 8. Found while writing the manual — open

Seen in the manual's first FSM2 Alptal project on 2026-10-01 (DeepSeek, released build). The model run itself passed; the project never reached **Completed**.

- **A plan step "written by the agent" can make Completed unreachable — medium.** Plans may contain steps with no tool (shown on the approval card as "written by the agent"; here `mass_balance_diagnostics`, offered as the recommended validation scope). Whatever such a step writes into `outputs/` or `artifacts/` has no run record, and `receipts.evidence` requires none to exist, so the project cannot complete unless those files are removed; the execution agent declined to delete them. Fix direction: refuse a tool-less step that declares file outputs at plan validation, or have the card say plainly that its files must stay outside the results folders.
- **The setup agent wrote results into the project, not only the shared folder — medium (extends issue 3).** Its example run left `outputs/alptal_2004_2005/*` in the project; they were listed as unreceipted files and blocked **Completed**.
- **A later failed attempt of a passed step fails the project — low/by design, but easy to trigger.** Completion uses each step's latest attempt. Asked to "finish", the agent re-ran tools for side purposes (a `--help` call, an attempt to route its own audit through a KI tool); each was bound to a plan step, failed validation, and turned the project to FAILED_VALIDATION. The agent's reply then said "validation: passed", which the receipts contradict. Consider ignoring failed attempts that write no declared outputs, or not binding `--help`-style probes to a step.
- **FSM2 parser `--plot` fails on Windows — low.** The KI's Python environment has no matplotlib (preflight checks only numpy and pandas), so `parse_fsm2_output.py --plot` raises `ModuleNotFoundError`; the agent fell back to GeoForge's plotting. Add matplotlib to the FSM2 Windows recipe or to its preflight.

## 9. Found during real CRHM / VIC / SHAW testing — local fixes and remaining validation

- **A Windows loader crash could be called ready.** SHAW's `0xC000007B` with empty output was recorded as runnable. The source verifier now rejects loader/crash/signal exits, including after a banner and in cached passes. A missing `libquadmath-0.dll` from its own compiler distribution was the observed SHAW runtime repair; the repaired program completed the official Trial.
- **VIC's version probe did not exercise configuration I/O.** The initial RC2 executable started but crashed on real input. Windows input-stream flushing/seek behavior lost configuration records; a zero-frame backtrace underflow then obscured the error. Repairs were reproduced on final 5.1.0, with real LF/CRLF example runs and deliberate invalid-input rejection. A usage probe remains installation evidence only.
- **SHAW readers assigned values to wrong variables/units/dates.** Water dates/columns, material-resolved net radiation, thaw/frost order and SWE units are corrected from authentic reference files. Hour 24 normalizes to the next midnight; four-digit years stay unchanged. Plots use actual node depths. The wrapper now preserves original controls, stages referenced uploaded inputs, and rejects stale, incomplete or malformed output as completion evidence.
- **CRHM input staging and identity needed care.** The wrapper stages original project/observation bytes and rejects conflicting or source-aliased destinations. The observed native program reports 4.7_16, while the manifest labels 1.3.5; that metadata discrepancy remains explicit. The assisted Boost acquisition and initial blocked attempt are retained in the evidence report.
- **CRHM timezone changed scientific output — fixed locally.** The ambient Windows timezone shifted dates and altered SWE (maximum observed difference 6.69605 mm). The runner now sets child `TZ=UTC0`; genuine repeated runs under two different ambient timezones produce byte-identical outputs. The original ambient result is superseded. The final Desktop run matches the corrected independent native output and has verified signed receipts.
- **Live model selection/review inconsistencies — fixed locally.** VIC classic-driver terminology and paths no longer add the separate CLASSIC KI. Approval now checks the selected project's materialized tools through the same execution-config boundary instead of rejecting them against catalogue roots; foreign project/KI tools and aliases still fail. Review cards no longer label future output paths as files already on disk.
- **SHAW managed paths, plotting and reruns — fixed and verified locally.** Preflight and execution resolve managed Windows binaries, plotting requires matplotlib, and an authorized rerun answers SHAW's overwrite prompt. Freshness and complete-output validation remain mandatory. Two native repeats and the final three-step Desktop run pass, with 65 focused passing tests; no stale output is accepted as a successful new run.
- **A genuine diagnostic log blocked SHAW's successful native receipt — fixed locally.** Numeric validation treated `shaw.stderr.log` as model data and returned a warning despite complete scientific tables. Explicit stdout/stderr log names now remain hashed diagnostic evidence without numeric checks. Generic model logs and scientific tables retain their existing validation; missing, empty, nonfinite or incomplete scientific outputs and process errors still block success.

After all code fixes froze, the final broad Desktop suite passed **1,633 tests, 35 skipped, 337 subtests** and shared Flow **190 tests, 5 skipped**. Python source hashes were unchanged throughout. Earlier 169 approval and 65 SHAW focused tests overlap this final coverage. All three Desktop completions are independently audited under `D:/GeoForge-E2E-20261001/runs/`, including `SHAW/final-verification.json`. Failed/stale receipts continue to block completion even when the agent reports success.

These fixes do not close the remaining Stop/Exit, calibration, CLI setup-enforcement, server-sync or all-model coverage gaps. No public release, installer installation/uninstallation, authenticated Database transfer or calibration acceptance is claimed.
