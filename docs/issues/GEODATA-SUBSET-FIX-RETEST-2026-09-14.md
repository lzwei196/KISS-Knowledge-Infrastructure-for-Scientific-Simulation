## Reproduce stale cached results

POST `/subsets/jobs` with:

```json
{"dataset_id":"hwsd_global","bbox":[115,37,115.1,37.1],"variables":[]}
```

Returns old job `35497839150e49e3`. Its output still has SHA-256
`9020053c6a0d73d82b85f28cc83664baa5df6351252d355b97b635e1a097b30c`,
288 raw bytes, not TIFF. Alias `hwsd_global_raster` reuses `c2783521191b401e`.

The nearby fresh bbox `[115.01,37.01,115.11,37.11]` produces jobs
`8f64d72406334f92` and `8044a5b7ff95409e`: both valid GeoTIFFs.

```json
{"dataset_id":"cn05.1_pre_daily_025","bbox":[115,37,117,39],"variables":[],"start":"1989-01-01","end":"1989-01-07"}
```

Still reuses job `7ee2ce4b2d7f4324`. File time axis is Jan 1–Dec 31, 365 samples.
Old manifest even says `time_subset_applied:true`, illustrating why that boolean
alone is not evidence of a correct time window.

Changing only dates to Jan 8–14 produces fresh job `2ad653cd6e694655`, 30,558 bytes,
time dimension 7, actual dates Jan 8–14. Manifest reports matching `time_range`,
`n_time_steps:7`, and `time_subset_applied:true`.

### Required cache fix

Include processing/schema version as well as source version and canonical request
in the result-cache identity. Invalidate or quarantine artifacts generated by the
buggy raster/time-slicing versions. Identical scientific requests should not need
artificially changed bounds/dates to receive corrected processing. This retest did
not delete server jobs or invalidate any user cache itself.

## Directory and projected-raster details

SoilGrids probe was `[115,33,115.1,33.1]`, inside its recorded catalogue coverage.
Other raster probes used `[115,37,115.1,37.1]` unless explicitly marked fresh.
CLCD/HWSD projected bounds were checked against an independent WGS84→native CRS
transformation, allowing pixel-window rounding. Raster values were finite and
categorical outputs integer-valued. No claim of full source-value parity is made.

An initial HWSD China test comparison incorrectly treated `OGC:CRS84` versus
`EPSG:4326` axis-order metadata as incompatible. The test was corrected to compare
equivalent CRS ignoring axis-order metadata for raster x/y; both actual files pass.
This was a test-check issue, not a backend failure.

Where the backend infers WGS84 from geographic-looking source bounds, preserve
`crs_source` provenance. Opening successfully does not independently establish
the original datum from authoritative source documentation.

## Service stability during regression

Initial targeted scan planned 154 records (previous positives/errors plus priority
fallback controls). During that scan the service temporarily returned HTTP 502 and
network failures. All eight first download-test estimates failed at the gateway.
The bulk scan was stopped after 97 saved results: 54 positive, 7 manual fallback,
32 HTTP 502 and 4 network errors. Those failures are preserved in
`output/geodata-subset-retest-2026-09-14/estimates-before-retry.json`.

At 2026-09-14 10:39:45 UTC, serial catalogue and small DEM checks recovered. Tests
continued serially. Cause of the outage is unknown; it is not attributed to load
or deployment without server logs. The test runner now pauses after three
consecutive gateway/network failures rather than continuing a failing batch.

## Evidence and boundaries

Final targeted estimate regression completed **154/154** records after recovery:
140 declared subsettable (95 nonzero estimates, 45 zero-byte selections), 14
structured non-subsettable responses, **no HTTP/network failures in the retained
completed matrix**. Earlier transient failures remain in the before-retry file.
Zero-byte capability responses do not establish usable data for the test area.
The earlier 61 successful responses were retained; interrupted/failed and untested
records were completed serially, not a second repetition of every successful call.
